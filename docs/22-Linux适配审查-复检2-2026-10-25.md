## 3. 两条"声称已修、实际仍失败"的 MAJOR

### 3.1 M4（FAIL）：`selftest_platform.py` 在 Linux 上恒 FAIL 1/21

- **位置**：失败断言 [`scripts/selftest_platform.py:73`](../scripts/selftest_platform.py#L73)
  ```python
  check('profile_base(win32)', p_win.endswith('tt-cdp') and os.path.isabs(p_win), p_win)
  ```
  根因 [`cdp_tools/platform_utils.py:140-142`](../cdp_tools/platform_utils.py#L140)：win32 回退用 `os.path.expanduser(r'~\AppData\Local')`，在 POSIX 上 `\` 不是分隔符 → 返回字面量 `~\AppData\Local`，拼成 `~\AppData\Local/tt-cdp` **非绝对路径**。
- **实测**（真仓库、干净副本均复现）：
  ```
  [4] profile 目录
    ❌ profile_base(win32)          ~\AppData\Local/tt-cdp
    ✅ profile_base(darwin)         /home/user/Library/Caches/tt-cdp
    ✅ profile_base(linux)          /home/user/.cache/tt-cdp
  ...
  结论: ❌ FAIL（21 项检查，失败 1，跳过 0）   rc=1
  # 无 CDP 隔离环境（unshare -rn）：20 项 + [9] 跳过 1，同样 FAIL 1、rc=1
  $ python3 -c "import os;print(os.path.isabs(os.path.expanduser('~\\\\AppData\\\\Local')))"
  False
  ```
- **影响**：`docs/20 §7` 让 Linux 用户把该脚本当验收命令；现在无论有没有 CDP 都是 **❌ FAIL / rc=1**，用户会误判"修复没生效"。`setup-linux.sh:49`、`README.md:96`、`docs/20:121/166` 的"应 PASS / 已修"在 Linux 上不实。
- **为什么 Windows 上没发现**：Windows 有 `LOCALAPPDATA`，`profile_base('win32')` 直接是绝对路径 → 断言通过。**与 M9 同源的盲区**。
- **修复（两处任选其一，建议都做）**：
  1. `selftest_platform.py:73`：跨平台断言应注入 env，如
     `p_win_env = pu.profile_base('win32')` 前设 `os.environ['LOCALAPPDATA']='/win/local'`，或改用 `ntpath.isabs(p_win)`；
  2. `platform_utils.py:141`：win32 分支用 `ntpath.join(ntpath.expanduser(r'~\AppData\Local'), 'tt-cdp')`，避免在 POSIX 上产出带 `~` 的相对串。
- **附带问题（同脚本）**：
  - `[9]`（[`selftest_platform.py:135-151`](../scripts/selftest_platform.py#L135)）**测不到 ego auto**：它只探 `TT_CDP_PORT`/`62202`/`9222-9231`，不调用 `discover('auto')`、不读 `browser.json`。隔离网络里把 fake CDP 放到 ego 的 45339，`resolve_port('auto')` 正常返回 45339，但 `[9]` 打印"当前没有 CDP 在跑"并跳过——`auto` 的修复没有被验收覆盖。
  - `[9]` 在 live 端口落于 9222–9231 时无鉴别力（`9222 -> 9222` 即使 `TT_CDP_PORT` 被忽略也会通过）。
  - `[3]`（[`:64`](../scripts/selftest_platform.py#L64)）对不存在的 `TT_BROWSER` 仍 ✅（`find_browser()` 返回字面量路径），与 `launch_cdp --check` 的 rc=2 不一致。

### 3.2 M6（FAIL）：`launch_cdp` 在"端口已有旧 CDP"时仍假成功

- **位置**：[`launch_cdp.py:187-203`](../launch_cdp.py#L187)。就绪循环是"**先探 CDP，再查子进程**"：
  ```python
  for _ in range(80):
      info = probe_version(port, timeout=0.8)
      if info:                       # ← 端口上任何 CDP 应答都会 break
          break
      if proc.poll() is not None:    # ← 只有"端口没 CDP"时才检查浏览器是否已退
          ... return 1
  ```
  因此只要端口上有**任何**旧 CDP，第一轮就 `break` 并打印 ready，`proc.poll()` 检查被绕过。
- **实测**（Lead 与 launcher 路各自独立复现）：
  ```
  # A) fake CDP 占住 :9480 + 浏览器启动即 exit 7
  $ TT_BROWSER=/tmp/failbrowser python3 launch_cdp.py 9480 about:blank
  [launch] ✅ CDP ready on :9480 (FakeCDP/1.0)
  launch rc=0                     # ← 浏览器根本没启动

  # A-real) fake CDP 占 :9651 + 真 Chrome（无 DISPLAY 必退）
  [launch] ✅ CDP ready on :9651 (STALE-OLD/1.0)   rc=0   随后 chrome pids=[]

  # 对照（端口无 CDP）——这一半确实修好了
  $ python3 launch_cdp.py 9630 about:blank   # 浏览器 exit 0
  [launch] ❌ 浏览器提前退出（exit code=0）   rc=1
  ```
  另有残余形态：真 Chrome 因 IPv4 被旧 CDP 占用而退到 `[::1]:<port>`，launcher 的 ready 指向**旧实例**（`127.0.0.1:<port>` 仍是旧 CDP），按 9222 优先接入会连错目标。
- **影响**：脚本/CI 在"上次浏览器还挂着 / 端口被占 / 新实例绑定失败"时得到 rc=0 与 `CDP ready`，正是 M6 要禁掉的失败模式；`scripts/ensure_browsers.py` 会继承这个 rc=0 并计入"就绪"。
- **修复（建议）**：Popen 前记录端口指纹，或就绪后校验归属：
  ```python
  # Popen 之前
  pre = probe_version(port)
  # 就绪判定
  ok = (info and proc.poll() is None
        and (pre is None or info.get('webSocketDebuggerUrl') != pre.get('webSocketDebuggerUrl')))
  ```
  更稳的判据：读 `<profile_dir>/DevToolsActivePort`（Chrome/Edge 会写 `<port>\n/devtools/browser/<uuid>`），要求首行 == 本次端口；失败分支要 `proc.terminate()` 收尾。
