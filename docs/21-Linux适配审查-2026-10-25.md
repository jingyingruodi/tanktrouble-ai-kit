## 2. 仍存在的 MAJOR（9 条，均已在新版复测）

> `git diff 7dd51b9 68db7b0` 证明以下相关文件**未被修改**；本次复检对每条都重新执行了复现命令（结果与初版一致）。

### M1. `ego_browser` 的 Linux state 目录取错 → `auto` 发现不到正在运行的 dsh-ego 浏览器
- 位置：[`cdp_tools/ego_browser.py:57`](../cdp_tools/ego_browser.py#L57)（用 `XDG_DATA_HOME` / `~/.local/share`）
- 证据（实测，`@68db7b0`）：本机 dsh-ego 浏览器（Edge pid 10199）确实在 `127.0.0.1:45339` 运行，`browser.json` 实际位于 **`~/.local/state/ego-lite-linux/browser.json`**（XDG **state** 目录）；而 `python3 cdp_tools/ego_browser.py` 输出"ego 浏览器未运行（无 browser.json）"，`probe(45339)` 却是通的。设 `EGO_BROWSER_STATE_DIR=~/.local/state/ego-lite-linux` 后立刻恢复 `source=ego port=45339`。DSH 侧运行时源码 `dsh-ego-browser/runtime/ego-linux/src/paths.mjs` 明确：profile 用 DATA_DIR，`browser.json` 用 STATE_DIR——**Windows 上两者同为 `%LOCALAPPDATA%`，所以在 Windows 验证永远看不到这个 bug**。
- 影响：Linux 上 `resolve_port('auto')` 对 dsh-ego 完全失效（回退扫描 9222–9231 也找不到随机端口）；`start-monitor.sh` 默认就是 `auto`。
- 修复：Linux 候选顺序改为 `XDG_STATE_HOME`/`~/.local/state` → `XDG_DATA_HOME`/`~/.local/share`，再拼 `ego-lite-linux` 等名称。

### M2. `TT_CDP_PORT` 在 `auto` 模式下被静默忽略，与文档/脚本提示相反
- 位置：[`cdp_tools/ego_browser.py:120-121`](../cdp_tools/ego_browser.py#L120)（只在 `preferred is None` 时读环境变量）；文档 [`docs/20:80`](20-Linux适配.md#L80)、脚本 [`setup-linux.sh:46`](../setup-linux.sh#L46)
- 证据（实测，`@68db7b0`）：`discover(preferred=None)`（环境变量 `TT_CDP_PORT=45339`）→ 命中 45339；`discover(preferred='auto')` / `resolve_port('auto')` → `RuntimeError`。而 6 个 auto 脚本、`monitor_server.py`、`tt.py` 传的正是字面量 `'auto'`。
- 影响：用户设 `TT_CDP_PORT` 想钉住端口，默认路径无视它 → 连到机器上另一个浏览器实例（静默连错目标），或直接报错。
- 修复：`if preferred in (None, '', 'auto'): preferred = os.environ.get('TT_CDP_PORT') or None`。

### M3. 文档推荐的"无显示器 = `xvfb-run … launch_cdp.py`"会在 launcher 退出瞬间杀死浏览器
- 位置：[`docs/20:49`](20-Linux适配.md#L49)、[`README.md:88`](../README.md#L88)、[`setup-linux.sh:52`](../setup-linux.sh#L52)；机制是 [`launch_cdp.py:87`](../launch_cdp.py#L87) 起子进程后 [:120](../launch_cdp.py#L120) 立即返回
- 证据（实测）：`xvfb-run -a … python3 launch_cdp.py 9456 about:blank` → 打印 `CDP ready`、rc=0，随后 Chrome 报 `X connection error received`，1–10 秒内 `/json/version` 全 `000`、chrome 进程 0（`xvfb-run` 回收了 Xvfb）。对照：手动常驻 `Xvfb :99` 则浏览器与 CDP 存活。
- 影响：无显示器服务器（Linux 适配的典型场景）"看起来成功、实际没有浏览器"；后续 monitor 永远"未就绪"，而 §8 排障表完全不提 Xvfb 已被拆。
- 修复：文档改成常驻 Xvfb 两步法（`Xvfb :99 … & export DISPLAY=:99` 再 `./launch-browser.sh 9222`），或 `xvfb-run -a bash -c 'python3 launch_cdp.py 9222; wait'`；代码可加 `--hold`。

### M4. `selftest_platform.py` 在"有浏览器在跑"（文档 §4 的正常状态）时误报 FAIL，且项数与文档不符
- 位置：[`scripts/selftest_platform.py:89-106`](../scripts/selftest_platform.py#L89)；文档 [`docs/20:98`](20-Linux适配.md#L98) 写"PASS（14 项检查）"
- 证据（实测，`@68db7b0` 复测）：无 CDP 时 13 项 PASS（[7] 被跳过）；用本地 fake CDP 模拟"浏览器已在 9222"（按 §4 正常启动后）→ **`❌ FAIL（14 项检查，失败 1）`**，失败项正是 `[7] discover() 采用 TT_CDP_PORT 9222`。原因：[7] 设 `TT_CDP_PORT=62202` 后调 `discover(preferred=None)`，62202 不通就回退扫描 9222–9231，只要那里有 CDP 就返回 9222，断言 `found == 62202` 必然为假。
- 影响：文档让人用 §7 自检"确认平台分支逻辑"，但按正常顺序操作必红；"14 项"这个数字只在 FAIL 场景出现。
- 修复：[7] 仅当 62202 有监听时断言，或只验证"`TT_CDP_PORT` 被读取"的优先级；文档改为"13~14 项（视 CDP 是否在跑）"。

### M5. 录制/自检命令依赖仓库里不存在且被 `.gitignore` 排除的目录 → 干净 clone 必失败
- 位置：[`scripts/selftest_monitor.py:94`](../scripts/selftest_monitor.py#L94)（`scripts/scratch/selftest_rec.jsonl`）、[`cdp_tools/recorder.py:40`](../cdp_tools/recorder.py#L40)（`open()` 不建父目录）、[`.gitignore:9/15`](../.gitignore) 排除 `data/`、`scripts/scratch/`；文档 [`docs/20:61`](20-Linux适配.md#L61)、[`README.md:63`](../README.md#L63)
- 证据（实测，复测仍缺目录）：`data/`、`scripts/scratch/` 均不存在；`Recorder('data/demo.jsonl')` → `FileNotFoundError`；`selftest_monitor` 的 [3/5] 录制报 `FileNotFoundError`，[4/5] 回放被连带打成误导性的 `ConnectionRefused`。**正反对照**：把仓库复制到 `/tmp` 并 `mkdir -p scripts/scratch` 后，同一命令全链路 ✅ PASS（16s、58 帧）。
- 影响：按文档逐字执行 → 录制命令报错、§7 的 `selftest_monitor` 无论有没有游戏都 FAIL，用户误判"Linux 适配坏了"。
- 修复：`Recorder.__init__` 里 `os.makedirs(os.path.dirname(outfile) or '.', exist_ok=True)`；`selftest_monitor` 自己建目录；`setup-linux.sh` 顺手 `mkdir -p data scripts/scratch`；文档补 `mkdir -p data`。

### M6. `launch_cdp.py` 会"假成功"：端口上已有旧 CDP 时，浏览器秒退也报 `CDP ready` + rc=0
- 位置：[`launch_cdp.py:87`](../launch_cdp.py#L87)（Popen 不检查）、[:93-101](../launch_cdp.py#L93)（只探 `127.0.0.1:<port>/json/version`，不校验归属）、[:120](../launch_cdp.py#L120)
- 证据（实测）：先在 9470 起一个 fake CDP，再用"启动即 `exit 7`"的假浏览器执行 `launch_cdp.py 9470 about:blank` → 输出 `CDP ready on :9470 (FakeCDP/1.0)`，**rc=0**，浏览器根本没启动。真实等价场景：上次的浏览器还占着 9222，新实例失败，脚本提示"就绪"、监控连到旧浏览器。
- 修复：保存 `proc`，轮询里 `if proc.poll() is not None: 报退出码 return 1`；就绪判定校验 `/json/version` 与 `proc.pid` 的归属。

### M7. `launch_cdp.py` 参数解析丢 URL：想开本地页，却静默打开在线游戏页
- 位置：[`launch_cdp.py:72-73`](../launch_cdp.py#L72)
- 证据（实测，`@68db7b0` 复测）：`TT_BROWSER=<记录 argv 的假浏览器> python3 launch_cdp.py "file:///tmp/local.html"` → 假浏览器实际收到 `https://tanktrouble.com/game`；用户传入的本地页被完全忽略且无警告（代码逻辑亦确定）。
- 影响：对一个在 `docs/19`、README 中声明"禁止在线对局"的套件，这会把只想开本地测试页的用户**带到在线游戏页**——合规风险 + 误导。
- 修复：改用 argparse（`port` 可选 int、`url` 独立）；或 `rest = [a for a in argv[1:] if a != '--check']` 再分别解析。

### M8. `kill-monitor.sh` 用"命令行子串"识别进程 → 会误杀非 Python 进程 / 用户包装 shell
- 位置：[`cdp_tools/platform_utils.py:189`](../cdp_tools/platform_utils.py#L189)（`if 'python' in cmd`）、[`scripts/kill_monitor.py:28-36`](../scripts/kill_monitor.py#L28)（`'monitor_server' in cmd`）
- 证据（实测，`@68db7b0` 复测）：起一个 argv 为 `vim python_monitor_server_notes.txt` 的 `sleep` 进程（非 Python），`python3 scripts/kill_monitor.py` 直接把它 SIGTERM 杀掉；另有多路实测：`tail -f …/python/monitor_server.log`、外层 `bash -c "… python3 monitor_server.py …"`、以及审查者自己的 3 个 shell 都被误杀。对照组：无关的 `python3 -c 'sleep(300)'` 不被默认模式杀。
- 影响：清理监控残留时可能杀掉用户的编辑器/日志查看器/CI 包装进程（SIGTERM 3s 后 SIGKILL，未保存内容会丢）。Windows 旧实现按 `name='python.exe'` 过滤，没有这个问题——**这是跨平台重写引入的回归**。
- 修复：用 `/proc/<pid>/exe` 或 argv[0] basename 判定解释器；脚本名按 token 精确匹配（`os.path.basename(tok) in {'monitor_server.py', …}`）；kill 前复核 cmdline。

## 4. 仍存在的 NIT（11 条）

1. `playback_server.py:23`、`ego_browser.py:18-20` 的 docstring 示例仍是 `C:\…` Windows 路径（跨平台入口里的残留）。

## 5. 根因：为什么"在 Windows 上验证过"仍会这样

1. **Windows 根本执行不到 POSIX 分支**：XDG state 目录、PEP 668、`xvfb-run` 生命周期、`ps` 解析都是 Linux 独有；M1 是最典型的例子——Windows 上 `browser.json` 与 profile 同在 `%LOCALAPPDATA%`，代码"看起来对"，到 Linux 就错。
2. **自检断言太弱，给了虚假安全**：`selftest_platform` 只验证"候选非空、路径以 tt-cdp 结尾、能看到自己进程、环境变量能覆盖"，恰好全部绕开了 Linux 的实际差异；它甚至在"有浏览器在跑"时自己 FAIL（M4）。
3. **自检脚本依赖本地未跟踪目录**：作者机器上 `scripts/scratch/` 存在（被 gitignore），所以文档写"PASS"；干净 clone 必失败（M5）。
4. **进程/端口策略是字符串启发式**：跨平台重写把 Windows 的 `name='python.exe'` 过滤换成 `'python' in cmdline`，精度反而下降（M8）。
5. **验收标准仍是"脚本语法通过"**：本次 docs/20 §10 的"`sh -n` 通过 / 引用文件存在"只能证明脚本可解析，不能证明 Linux 上可运行——真正需要的是本报告 §7 的实机命令序列。

## 8. 结论

- **Linux 适配的主干（`platform_utils` 抽象、`launch_cdp` 的 Linux 分支、monitor/录制/回放链路）是真能用的**，本次复检在 Debian 13 + Chrome 156 + Python 3.13 上逐项验证；初版的安装 BLOCKER 已由 `68db7b0` 修复。
