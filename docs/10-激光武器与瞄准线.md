## 1. 激光相关对象（游戏内部）

| 名字 | 作用 |
|------|------|
| `LaserWeapon` | 激光武器类（静态 `createInitialWeaponState` 给出初始状态） |
| `AimerUpgrade` / `LaserAimerUpgrade` | **瞄准线（虚线）是一个 upgrade**，静态 `createInitialUpgradeState` |
| `UIAimerGraphics` | **画瞄准线的类**（`update / _castRay / spawn / activate / strengthen / weaken / remove / retire`） |

## 2. 瞄准线算法（`UIAimerGraphics.update()` 完整还原）

```js
if (!this.exists || paused) return;
if (!this.activated) return;
const positions = [];
let remainingLength = this.maxLength;              // ★ 总长度预算，由 spawn(pid, maxLength, activated) 传入
const tank = gameController.getTank(this.playerId);

// ① 起点 = 车体中心 + 朝向 × 炮口偏移
positions.push({
  x: tank.getX() + sin(rot) * UIUtils.pxm(UIConstants.AIMER_OFFSET),
  y: tank.getY() - cos(rot) * UIUtils.pxm(UIConstants.AIMER_OFFSET),
});
let rayDir = { x: sin(rot), y: -cos(rot) };        // 朝向单位向量

// ② 逐段射线 + 镜面反射，直到长度用尽 / 撞到坦克 / 撞到出生点
while (remainingLength > 0) {
  const start = positions[last];
  const end = start + rayDir * remainingLength;
  const r = this._castRay(start, end);
  if (r.hasHit) {
    positions.push(r.hitPoint);
    if (r.hasHitTank || r.hasHitSpawn) break;                       // 命中坦克/出生点 → 停
    remainingLength -= Math.max(UIConstants.AIMER_MIN_STEP_LENGTH, r.hitDistance);
    rayDir = reflect(rayDir, r.hitNormal);                          // 镜面反射
  } else { positions.push(end); break; }                            // 没打中任何东西 → 画到尽头
}
// ③ 把 positions 画成"一段实、一段空"的虚线（段长由 QualityManager 的画质档位决定 + 随机相位）
```

### `_castRay(start, end)` —— 用的是 **p2.js**，不是 Box2D

```js
const ray = new p2.Ray({
  mode: p2.Ray.CLOSEST,
  from: [-start.x, -start.y], to: [-end.x, -end.y],   // ★ 坐标取负：p2 世界是镜像坐标系
  skipBackfaces: true,
  collisionMask: wall | tank | shield | spawn,        // 墙/坦克/护盾/出生点 都会挡住射线
  collisionGroup: rayCollisionGroup,
});
world.raycast(result, ray);
// 返回 {hasHit, hitPoint, hitNormal, hitDistance, hasHitTank, hasHitSpawn}
```

### 数值常量（实测）

| 常量 | 值 | 含义 |
|------|----|------|
| `UIConstants.AIMER_OFFSET` | **50**（像素） | 起点沿炮口前移量 |
| `Constants.METERS_PER_PIXEL` | **0.05** | 20 像素 = 1 米 |
| → 实际炮口偏移 | **50 × 0.05 = 2.50 m** | **与"从真实弹丸反推"的 2.50 m 完全一致（两条独立证据）** |
| `UIConstants.AIMER_MIN_STEP_LENGTH` | 0.01 | 每次反弹至少推进量（防死循环） |
| `UIConstants.AIMER_WIDTH` | 4 | 虚线宽度 |
| `UIConstants.LASER_RETRACTION_TIME` | 0.05 | 激光光束回收时间 |

> `UIUtils.pxm(v) = v * Constants.METERS_PER_PIXEL`；`UIAimerGraphics.spawn(playerId, maxLength, activated)`
> 说明**虚线长度上限由调用方传入**（每个实例一个 `this.maxLength`）——这就是玩家感觉"虚线长度有限"的来源，
> 具体数值需要拿到激光后读活对象 `aimerGroup.children[*].maxLength`，或从 `AimerUpgrade.createInitialUpgradeState` 找。

## 3. 对我们弹道模型的意义（重要）

| | 我们现在用的 | 游戏自己的瞄准线 |
|---|---|---|
| 物理引擎 | **Box2D**（`B2DUtils.calculateProjectilePath`，坦克 `getB2DBody().GetWorld()`） | **p2.js**（`game.physics.p2.world.raycast`） |
| 起点 | 车体中心（默认；`muzzle_offset` 参数可改，已证伪） | **炮口 = 中心 + 2.50 m** |
| 终止 | 命中坦克 / 反弹上限 / 长度上限 | 命中坦克或出生点即停；撞墙反射；长度预算 `maxLength` |
| 坐标 | 世界坐标（米） | 镜像（`from:[-x,-y]`） |

**结论**：
1. 我们 v8/v9 的假命中，恰恰是"**用错引擎 + 错起点**去判断能否命中"的典型症状；游戏自己的瞄准线用 p2 + 炮口起点，反而和真实表现更贴近（至少起点是对的）。
2. 但**瞄准线不是权威真值**：它是客户端渲染侧的近似（p2 世界 + 长度上限 + 撞坦克即停），权威仿真在服务端。
   所以正确的用法是：**拿它当参考信号做交叉验证，最终仍以"真实开火 + 录制弹道"为准**。

## 9. 激光参数实测（2026-10-02 实机）

### 9.1 参数表

| 参数 | 实测值 | 依据 |
|------|--------|------|
| 弹速 | **180.0 m/s 恒定**（不衰减） | 逐帧采样 `getSpeedX/Y` |
| 寿命 | **≈0.80 s**（`timeAlive` 0.017 → 0.801 后消失） | 逐帧采样 |
| 弹药 | **1 发**：射击后 `getActiveWeapon` 立刻回到基础弹 `-1` | 射击前后状态对比 |
| 反弹 | **镜面反射**，本发实测 **5 次** | 反射拟合重建 |
| 路径总长 | **141.1 m**（= 180 × 0.784 s，理论值 141.1 m，误差 0.0 m） | 反射拟合重建 |
| 开火指令 → 弹丸出膛 | **9.8 ms** | 页面时钟对齐 |
| `Constants.LASER_LOCK_TIME` | **0.2** | 常量直读；**不是发射前摇**（否则出膛应 ~200ms） |
| `Constants.AIMER_LENGTH` | **60**（虚线长度预算，= 实测 `aimer.maxLength`） | 常量直读 |
| 仿真 tick | **16.7 ms（60Hz）→ 每 tick 弹丸跳 3.06 m** | `timeAlive` 步长分布 |
| 炮口偏移 | **2.50 m**（`AIMER_OFFSET=50px × METERS_PER_PIXEL 0.05`） | 常量 + 弹丸反推，两条独立证据 |

武器状态字段：`LaserWeapon` 只有 `{_fired, _timeSinceFire}` —— 一发即消耗，`_fired` 记录是否已发射。

### 9.2 关键方法论：为什么"提高录制频率"没用

激光 180 m/s，而**位置每 tick 才更新一次**（60Hz，3.06 m/tick）。
采样快于 tick 只会拿到重复位置，**信息量不会增加**。要精确还原弹道，正确做法是：

**逐帧采样（60Hz，即上限）+ 相邻采样点之间做"反射拟合"**
（`scripts/laser_reconstruct.py`）：

```
已知：匀速 180 m/s、只做镜面反射
每个 leg 看成几何题：初始方向未知，总长 = 180 × ΔtimeAlive 已知
  → 以弦方向为中心搜索初始角 θ（±15°，先 1° 粗搜再 0.05° 细搜）
  → 用**游戏自己的 p2 射线**（与 UIAimerGraphics._castRay 同参数）逐步前进：
      撞墙 → 镜面反射继续；走满 L 为止 → 得终点 E(θ)
  → 取 |E(θ) − B| 最小的 θ
```

这样**即使一个采样间隔（3.06 m）里发生两次反弹也能还原**，反弹点由游戏自己的
collision world 给出，精度到毫米级。单 leg 拟合残差同时是**质量指标**：
本发 47 个 leg 大多 0.005 m，仅 4 个 1.2~1.4 m（贴墙擦碰/拐角段）。

> 对比：直接"按帧间朝向数反弹"会得到 17 次（3 m 步长 + 贴墙抖动导致），
> 而拟合结果是 5 次 —— **靠采样密度数反弹不可靠，必须做几何拟合**。

### 9.3 与瞄准线预测的关系

官方虚线**同样会反弹**（同一 `_castRay` + 镜面反射 + `AIMER_LENGTH=60` 预算），
所以"官方预测"和"真实弹道"在**行为上一致**，差别只在：
预算长度（60 m 截止 vs 实际飞到 141 m）、以及原点（炮口 2.5 m）。
这为下一步（把 p2 预测接进火控）提供了直接的对照基准。

## 10. 官方"命中预测"的边界 + 我们自己的命中层（2026-10-02）

### 10.1 官方有什么、没有什么（实测）

拿官方 `_castRay` 从 8 个方向朝目标坦克打射线：

```
命中 group=8（tank）✓  距离 3.81~4.39m（与车体实际尺寸一致）
但 shape.body 上只有 {id, idleTime}，没有 playerId/sprite → pidsMatch = []
```

| 能力 | 官方 | 说明 |
|------|------|------|
| 撞墙/护盾/出生点/坦克的**几何检测** | ✅ | `hasHit` + `hasHitTank`/`hasHitSpawn` |
| **认得出打的是哪辆坦克** | ❌ | 所有坦克共用一个 collisionGroup（8），shape 上无身份信息 |
| **弹丸半径** | ❌ | 零半径射线；真实弹丸有粗细，擦边会判 miss、贴墙擦弹会判 hit |
| **目标移动提前量** | ❌ | 静态快照 |
| **真实射程** | ❌ | 长度被 `Constants.AIMER_LENGTH = 60m` 截断，不是武器寿命决定的射程 |
| 是否会被自己打死 | ❌ | 自车与敌人同样算 `hasHitTank` |

**结论：弹道用官方的，命中预测我们自己加。**

### 10.2 我们加的命中层（`scripts/official_aim.py`）

```
1) 官方 p2 射线走折线：炮口起点 2.5m → 镜面反射 → 撞墙/护盾/出生点止（**不挡坦克**），
   预算 = 武器真实射程 = 弹速 × 寿命
2) 半径感知命中判定：对每辆坦克算"圆心到各折线段最短距离" ≤ 坦克半径 + 弹丸半径 → 命中，
   取沿路径**最早**的那个 → 天然得到身份（自车/目标/其它）
3) 自伤规则用游戏自己的字段（见 10.3）
4) 页面内角度扫描（1° 粗扫 + 0.1° 细扫），一次 CDP 调用出结果
```

### 10.3 从 v7 真实录制标定出的三条关键规则

对 `fire_strict_v7.jsonl`（28362 帧、163 发弹丸）统计：

| 发现 | 数据 | 影响 |
|------|------|------|
| 弹丸字段自带 `lifetime` / `maxLifetime` | 基础弹 `maxLifetime = 10 s` | 射程预算 = 18 × 10 = **180m** ✓（与我们的默认一致） |
| **真实反弹次数可以很高** | 分布 0×125、1×22、2×6、3×4、4×2、5、6、**13** 各 1 | 我们旧火控 `bounces ≤ 4` 的过滤**过于保守，漏掉大量有效解**（可能是跳过率 20~27% 的原因之一） |
| **`deadlyToOwner` 在第一次反弹时翻转为 true** | 43 个可观测翻转中：翻转帧 == 首次反弹帧 23 个，"早 1 帧"（采样边界）约 15 个，例外 2~4 个 | **直射弹打不死自己；只有反弹之后才可能自伤** —— 直接取代 `self_radius_slope` / `path_hits_self` 一类启发式；v4 那次"3 次反弹自杀"完全吻合 |

因此自伤判定简化为：**只检查"首次反弹之后"的路径段**（加上炮口出膛段豁免）。

## 12. 逐武器实测（步骤 1，2026-10-02）

### 12.1 实测结果

| 武器 | 一次扣扳机发数 | 散布（相对炮管） | 弹速 m/s | 出膛延迟 | 蓄力 |
|------|---------------|------------------|----------|----------|------|
| Bullet 基础弹 | 1 | **0.00°**（恒定，对照） | **18.0** | — | 无 |

### 12.2 由此发现的两件重要事情

1. **各武器弹速差异巨大**：基础弹 18、加特林 25~30、霰弹 30~35、激光 180 m/s。
   旧模板里"除激光外都用 18 m/s"的假设是错的 → 火控的提前量/射程预算必须按武器取速度。
2. **同一武器不同弹丸的初速可以不同**（加特林 25.4~29.6、霰弹 30.5~34.9，且每发自始至终恒定）
   → 除了**角度散布**，还有**速度散布**，两者一起决定命中不确定性。
   本模块的 `hit_radius_with_spread()` 处理角度散布；速度散布会额外放大远距离落点误差。

3. **加特林有预热（蓄力）≈0.5s**：扣扳机后需持续按住约 0.5s 才出弹，
   之后出弹数随按住时长增加（0.8s→3、1.2s→7、2.5s→10）。
   任何"开火即出弹"的假设对加特林都不成立 → 火控里必须先把蓄力算进时间线。

  → 驻留期间后台保活（>35s 无输入就发 0.55s 脉冲），结束强制退房；
* **回合切换**会让坦克清空 → 操作前等 `model.getState() == 'in round'`，找不到坦克先等重生。

## 16. 地图（maze）get 与视觉核对（2026-10-02，用户要求）

### 16.1 结论：**地图获取是正确的**，但**语义必须搞清楚**

四方对照（同一张迷宫，`scripts/verify_walls_four_way.py`）：

| 来源 | 说明 | 与 REF 的一致度 |
|------|------|----------------|
| **REF** `maze.getWalls()` | 游戏自己的墙体清单（每条含 `x,y,flipX,flipY,rotate,number`） | — |
| **SPR** 渲染墙体精灵 `mazeWallGroup` | **画面上真正看到的墙** | **100%** |
| **TILE** `tiles[x][y] = [present, topWall, leftWall]`（监控室用法） | 监控室据此画 top/left 墙边 | **100%** |
| PATH 我用寻路推断的"墙格" | 相邻格"需绕行"→ 认为该格是墙 | 54.5% ❌ **推断方法本身错** |

并且 **`getWalls()` 条数 == 渲染精灵个数**（实测 67==67、59==59）→ 渲染器就是消费这份清单。

### 16.2 关键语义（之前误解的地方）

* `tiles[x][y]` 的 **`[0]=present`（该格是否有地板）、`[1]=topWall`、`[2]=leftWall`**；
  `present=0` 表示整格封死（监控室此时四边都画墙），**不是**"可通行为 0"。
  我先前把 `tile[0]` 当"可通行"标志做核对 → 得出错误的"地图取错了"结论（已纠正）。
* **`getWalls()` 列出的是"含墙边/墙饰的格子"**（墙画在格子边沿），因此**"有墙条目"≠"不可通行"**：
  坦克完全可以站在含墙条目的格子里（截图实证：坦克位于这些格内正常行驶）。
* **要判断能不能走，必须用**：游戏自己的 `maze.getShortestPathWithGraph({x,y},{x,y})`
  （连通性权威），或 `topWall/leftWall` 边标志；**不要**用"该格有没有墙"来判路。

### 16.3 视觉核对（截图）

截图（`ego_screenshot`）显示：Deathmatch 螺旋式竞技场 + 我方 3 辆坦克在下方玩家栏、
场上金币/道具箱/装饰。画面中的墙是**穿过大多数格子的连续墙带** ——
与"73 条墙条目分布在 63 格里（多数格含 1~2 条）"完全一致；
若按我早先"多数格不可通行"的误读，就会与画面（大片可行驶地板）矛盾。
**结论：数据与画面一致，之前的矛盾源于语义误读。**

### 16.4 需要改的地方

* `scripts/verify_maze_vs_visual.py` 里那段"不可通行格"的推算用的是旧误读 → 已标注纠正；
* `scripts/pickup_weapon.py` 的 `spawnCrate` 兜底扫描里 `tiles[x][y][0]` 表示"有地板"，
  语义没错但**不能保证该格周边无墙** → 仅作兜底（首选游戏自带 `getRandomUnusedPosition`）；
* 监控室 `monitor_server.py` 的墙提取（`[present, topWall, leftWall]`）**经本次核对是正确的，无需修改**。

## 17. 武器参数实测补完（2026-10-02，主线第 1 步）

### 17.1 新方法：读"武器内部状态"，不再数弹丸

数弹丸的老办法在实测中反复失败：**自己打出的弹丸会把人打死 → 回合重置 → 武器被清空**，
采样直接断掉（本轮实测连续 4 次 `queue: []` 拾取失败）。

新工具 `scripts/measure_charge.py`：按住扳机时在页面内以 60Hz 逐帧采样
**武器自身字段** `_weaponCharge / _triggerPulled / _numBullets / 弹丸数`，
顺带 dump 该武器实例的**原型链实现**（fire/charge/update 源码）→ 得到权威参数，
完全不受弹丸是否存活、回合是否重置影响。

### 17.2 装备参数（已写入 `cdp_tools/official_ballistics.py` 的 `WEAPONS`）

| 武器 | 弹速 | 出膛延迟 | 蓄力/预热 | 射速 | 散布 | 弹仓 |
|------|------|---------|----------|------|------|------|
| bullet（基础） | 18.0 m/s | — | 0 | — | 0.00° | 5 |
| laser | 180.0 m/s | 9.8 ms | 0 | — | 0.00° | 1 |
| **double_barrel** | 18.0 m/s | **9.0 ms** | 0 | — | **0.00°** | **10** |
| shotgun | 32.0 m/s | 6.3 ms | 0 | — | σ≈4.0° | 20 |
| **gatling_gun** | 27.0 m/s | — | **486 ms** | **119 ms/发（≈8.4 发/s）** | σ≈1.58° | **20** |

### 17.3 加特林：蓄力过程逐帧实录

```
扳机按下: charge=0.032, numBullets=20
charge 线性爬升: 每帧 +0.0334 → 每 ms +0.00206（1.0 满蓄力 ≈ 486 ms）
★ 首次出弹: t=+486 ms, charge 恰为 1.00
出弹时刻: 486/601/719/835/952/1069/1203/1320 ms → 间隔稳定 119 ms（115~134）
弹仓 20；打空后武器 type 5 → -1（自动切回基础弹）
```

**在线含义**：在线输入粒度 0.5s，而蓄力就要 486ms → **在线必须按住 ≥0.6s 才可能出弹**，
这解释了"在线轻轻点一下没子弹"（与 §15.2 的输入粒度结论一致）。

### 17.4 双管：一次扳机 = 一发

```
扳机按下当帧（≤17ms 内）: numBullets 10→9，弹丸 proj=1
随后按住 2.2s: numBullets 恒 9、proj 恒 1 → 没有第二发
charge=None（该武器无蓄力字段）
```
即 "DoubleBarrel" 的名字**不体现为一次两发**：偏差恒 0.00°、弹速 18.0 m/s、10 发弹仓。

## 18. 在线弹道复核（2026-10-16，主线第 2 步）

### 18.1 方法：复用上个 agent 的录制管线 + 受控在线房间

* **录制**：`scripts/record_only.py <port> --out X.jsonl --fps 60 --compress`
  （被动采样监控室 `STATE_JS` 全量状态 → `CompressedRecorder`；这条管线是上个 agent 就留下的，
  比我临时写的页面内 rAF 采样更稳、字段更全）；
* **开火**：`scripts/fire_burst.py auto --duration N --hold 0.8 --gap 2.2`
  （★ 必须用"持续作战模式"：受控房里全是我们自己的坦克，己方弹丸弹回来会打死自己人 → 回合重置，
  固定串数必然半途失败，改成"在场就打、不在场等重生"）；
* **验证**：`scripts/validate_ballistics.py X.jsonl auto` —— ⚠️ **必须在房间里跑**，
  页面内预测需要活的 game controller（退房后 `gc` 为 null 会崩）。

### 18.2 结果（19 发，全部 180m 全程，每发约 325 帧）

```
路径长度：真实 180.0~181.2m   vs   预测 181.8~183.0m      → 长度误差 中位 2.11m（≈1.2%）
观测点 → 预测折线 距离：中位 0.433m  平均 0.605m  最大 ≈1.09m   （相对 180m ≈ 0.24%）
预测折线 → 观测点 距离：中位 0.687m  平均 0.749m
反弹次数（启发式）：真实 15~19 次  vs  预测 5 次
```

### 18.3 结论

* **我们的官方弹道复现在线可用**：180m、十几次反弹的长路径上，与真实轨迹的偏差**亚米级（中位 0.43m）**
  —— 对火控瞄准而言这是"足够准"的量级；
* **反弹计数差异（15~19 vs 5）不是轨迹错误**：验证器的"真实反弹"是逐帧方向变化 >25° 的启发式计数，
  而模型只在**墙体交点**计一次（墙角/连续反射会合并），两把尺子口径不同。
  判据应以**轨迹偏差**为准（0.43m），而不是这个计数；
* 长度误差 1.2% 与"弹速按武器恒定"的假设一致（真实弹速在 25~34 m/s 间因武器而异，见 §17）。

### 18.4 对第 3 步（接进火控）的直接结论

* 官方轨迹 + 自建命中层**可以直接用于火控**，无需再改弹道模型；
* 火控侧要放宽的是**搜索上限**（老的 `bounces ≤ 4`、`max_travel = 45m`）——
  实测在线长弹道 180m、十几次反弹都真实存在，收得太紧会漏掉可用解；
* 验收标准：离线用录制数据核对 + 在线受控房打若干回合（命中率/自伤率/跳弹次数）。

### 18.5 运维要点（在线采样）

* 受控房（全是我们自己的坦克）里**己方弹丸会打死自己人** → 采样脚本必须容忍回合重置；
* 录制与开火要**并行**（`Start-Job` 跑 `record_only.py`，主进程跑 `fire_burst.py`）；
* 采样结束**先验证、后退房**；退房用强制退出（`leaveGame(true)`）。
