## 2. 仍未修好：M6 的"循环耗尽"漏洞（含新回归）

### 2.1 [FAIL] 旧 CDP 常驻 + 浏览器存活 → 30s 后仍假成功
- **位置**：[`launch_cdp.py:187`](../launch_cdp.py#L187)（`pre_ws` 指纹）、[`:213-227`](../launch_cdp.py#L213)（就绪循环）。
- **根因**（读代码即确定）：
  ```python
  for _ in range(120):
      if proc.poll() is not None: return _fail(...)     # 只在这里判"浏览器已退"
      info = probe_version(port, timeout=0.8)
      if info:
          ws = info.get('webSocketDebuggerUrl')
          if pre_ws and ws == pre_ws:
              time.sleep(0.25)
              continue          # ← 只 continue，没有把 info 清空
          break                 # ← 只有指纹变化才算"接管"
  if not info:                  # ← 循环耗尽时 info 仍是旧 CDP 的 dict，所以永远不成立
      return _fail(...)
  print('✅ CDP ready on ...')  # ← 于是 30s 后打印 ready + rc 0
  ```
  即"旧 CDP 指纹不变"这条分支只做到"继续等"，**没有在等待耗尽后判失败**。
- **主审独立复现**（真 Chrome + Xvfb）：端口 9485 先放一个带稳定 `webSocketDebuggerUrl` 的 fake CDP，再用真 Chrome 启动：
  ```
  [launch] ⚠️ 端口 :9485 已有 CDP 在监听（FakeCDP/1.0）；将校验是否由本次实例接管
  [launch] ✅ CDP ready on :9485 (FakeCDP/1.0)
  launch rc=0 elapsed=30s
  leftover chrome procs: 10        # 没有 terminate、浏览器成孤儿
  ```
- **并行路复现**：真 Chrome 场景 `:9803` 30.9s / `:9806` 30.1s，同样 rc=0 并残留 10 个 Chrome；把副本 `range(120)` 改成 `range(2)` 后 **0.55s** 即复现同一假成功（证明不是超时问题，是判定问题）。
- **建议修复**（加 `owned` 标志，并在失败时清理子进程）：
  ```python
  took_over = False
  for _ in range(120):
      if proc.poll() is not None: return _fail(...)
      info = probe_version(port, timeout=0.8)
      if info:
          if pre_ws and info.get('webSocketDebuggerUrl') == pre_ws:
              info = None                    # 关键：旧指纹不算成就
              time.sleep(0.25); continue
          took_over = True
          break
      info = None
      time.sleep(0.25)
  if not took_over:
      return _fail('端口 %d 仍被旧 CDP 占用（本次实例未接管）' % port)
  ```
  更稳的判据是读 `<profile>/DevToolsActivePort` 并要求首行 == 本次端口。

### 2.2 [NEW-ISSUE] 同 profile/端口已有健康实例时，重复启动被误判失败
- **位置**：[`launch_cdp.py:214-215`](../launch_cdp.py#L214)（`proc.poll() is not None` 即判"提前退出"）。
- **实测**：先 `launch_cdp.py 9804 about:blank` 成功（Chrome 存活、CDP 正常）；再执行同一命令 → Chrome 检测到同 `--user-data-dir` 已有实例，把参数交给旧实例后自身以 0 退出：
  ```
  [launch] ⚠️ 端口 :9804 已有 CDP 在监听（Chrome/156.0.8078.47）；将校验是否由本次实例接管
  [launch] ❌ 浏览器提前退出（exit code=0）   rc=1
  # 但 :9804 的 CDP 完全健康（ws 可连、页面正常）
  ```
  旧版（`d38b364`）此场景 rc=0。**影响**：重复执行 `./launch-browser.sh 9222` 会看到"失败"而实际浏览器正常（`ensure_browsers` 因先 `probe()` 跳过在线端口，暂未暴露）。
- **建议**：若 `pre` 存在且 `proc` 以 0 退出 → 打印"已有实例在运行"并 `return 0`（或明确 `rc=2` 的"复用"语义），不要当作失败。

## 3. N9 的修复是死代码（`terminate` 重复定义）

- **位置**：[`cdp_tools/platform_utils.py`](../cdp_tools/platform_utils.py) —— `script_token_match` 在 `:284` 与 `:357` 各一份（文本完全一致）；`terminate` 在 `:323`（新版，含 `_posix_zombie` + Windows `returncode`）与 `:386`（旧版）各一份。
- **实测（AST + 运行时）**：
  ```
  DUPLICATE: script_token_match at lines [284, 357]
  DUPLICATE: terminate at lines [323, 386]
  pu.terminate.__code__.co_firstlineno == 386      # 生效的是旧版
  'pu.terminate.__code__.co_names' 中无 _posix_zombie
  ```
  ```
  僵尸子进程 terminate(grace=1.0)：生效版 1.001s 返回 True；新版实现 0.000s
  不存在的 pid (999999)：生效版 False（应为 True）；新版 True
  Windows taskkill rc=1（模拟）：生效版 True（无视返回码）；新版 False
  ```
- **影响**：`kill_monitor` 拿到的仍是旧 `terminate`；对已退出/僵尸目标白等 grace（3s/个），枚举后自行退出的进程会被报"终止失败"并可能让 `kill_monitor` rc=1（假失败）；Windows 上失败也报成功。
- **原因推测**：补丁被重复应用了一次（新实现追加在后，旧实现未删除）。**建议**：删除 `:357-383` 与 `:386-404` 两段旧副本（`script_token_match` 重复块可整段删；`terminate` 保留 `:323` 新版），并加一个"模块内无重复 `def`"的静态测试。
