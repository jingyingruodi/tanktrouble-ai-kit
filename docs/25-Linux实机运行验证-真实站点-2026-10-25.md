## 2. 真站点 / 真 bundle 才暴露的问题

### R1（阻塞级）补丁脚本在宿主侧下载 bundle，被 Cloudflare 403
- 位置：[`scripts/patch_frontend_api.py:226`](../scripts/patch_frontend_api.py#L226)、[`scripts/inject_api_bootstrap.py:151`](../scripts/inject_api_bootstrap.py#L151)（`urllib.request.urlretrieve(bundle_url, …)`）
- 实测：浏览器里页面/资源都正常，但宿主 `urllib` 请求 `https://tanktrouble.com/build/js/index-4YALVKHK.js` → **HTTP 403 Forbidden**
  （默认 `Python-urllib` UA，且无浏览器 Cookie/Referer；即使加了 UA，直连也可能被 TLS/分流拦截）。
- 影响：干净环境下 `patch_frontend_api.py` / `inject_api_bootstrap.py` 第一步就崩，页面 API 无法恢复，后续所有脚本不可用。
- 建议：优先用**浏览器自身**取 bundle：
  1. 已加载资源：CDP `Page.getResourceContent(frameId, bundleUrl)`；
  2. 未加载时：页面内 `fetch(bundleUrl).then(r=>r.text())`（`Runtime.evaluate` + `awaitPromise`）；
  3. 两者都失败再回退 `urllib`（并带上浏览器 UA/Referer，或读取 `--proxy` 参数）。
  本次即用方案 1 从缓存取出 1,954,941 字节 bundle，存入 `scripts/scratch/` 后补丁成功。

### R2（阻塞级）项目 CDP 客户端默认 1 MB WebSocket 帧，取大 bundle 会被 1009 断开
- 位置：[`cdp_tools/cdp.py:99`](../cdp_tools/cdp.py#L99)（`websockets.connect(self.page_ws_url)` 未设 `max_size`）
- 实测：bundle 1.95 MB；用 `cdp_tools.CDP` 取回时触发
  `ConnectionClosedError: sent 1009 (message too big) frame exceeds limit of 1048576 bytes`。
  （`patch_frontend_api.py` 自己的会话设了 `max_size=128MB`，但通用 `CDP` 类没有。）
- 影响：任何经 `CDP.eval()` 返回大数据的操作（抓 bundle、截大图、导出状态）都会断连。
- 建议：`CDP.__init__` 增加 `max_size`（默认 16–32 MB），或对大数据改用 `Network.getResponseBody` / 分块读取。

### R3（环境相关）Chrome 不读 `http_proxy` 环境变量；直连被挡时 `launch_cdp.py` 没有代理选项
- 位置：[`launch_cdp.py`](../launch_cdp.py)（构建参数处，无 `--proxy-server`）
- 实测：本机直连站点时好时坏（TLS 超时/EOF）；本次可用 dsh-ego-browser（插件已配置代理）。
  用项目自带的 Chrome 复现时，可通过 `TT_BROWSER` 包装脚本追加 `--proxy-server=http://127.0.0.1:2233` 解决。
- 建议：`launch_cdp` 支持 `TT_CHROME_PROXY` / `--proxy-server`（可选），并在 docs/20 排障表补一条。

### R4（小）`tt.py scan` 忽略端口参数，固定扫 9222–9241
- 位置：[`tt.py:153`](../tt.py#L153)（`for port in range(9222, 9242)`）
- 实测：`tt.py scan 45339` 仍去扫 9222 段，命中了另一台测试 Chrome（未打补丁 → `GameManager=undefined`）。
- 建议：`scan` 接受 `auto`/端口（或复用 `ego_browser.discover`）。

### R5（文档）"首次跑"缺少"必须先补丁"的串联步骤
- `docs/01`/`docs/03` 的快速开始默认"页面加载后 `GameManager` 可用"，但 2026-10-16 前端改版后必须先跑
  `patch_frontend_api.py`（docs/11 有说明，但入口页没有串起来）。
- 建议：在 docs/20 §5 或 docs/01 §5 的"自动开本地局"前加一行
  `python3 scripts/patch_frontend_api.py auto --keep-open`，并注明 403/1MB 的两个常见失败模式（R1/R2）。

## 3. 结论

- **项目实际可以跑起来**：在真实官网页面 + 本地双人局上，连接、状态、开局、监控（9310 两辆坦克）、录制（49 帧）、
  回放（9316）、控制（5/5）全部通过；截图与录制样本见上。
- **前提条件**（缺一不可）：
  1. 网络可达（本次靠用户调整代理分流；ego 浏览器已带代理配置）；
  2. 用 dsh-ego-browser 或带代理的 Chrome；
  3. 按 docs/11 运行 `patch_frontend_api.py auto --keep-open` 恢复 API（本次需先从浏览器缓存取 bundle，见 R1/R2）；
  4. 用 `scripts/start_local_game.py` 开 **Local 局**（不要进在线匹配）。
- **建议优先修 R1/R2**：它们会让"新环境首次运行"在第一步失败，且失败信息（403 / 1009）不指向真正原因。

## 5. 附加：击杀验证（本地双人局，2026-10-25 追加）

在 §1 的实跑之后，用 `kit/ttkit` 的 `aim_and_fire` 让 Player 1 消灭 Player 2，验证完整火控闭环：

- 角色：`<pid-1>=arrows`（Player 1，主控）→ `<pid-2>=keyboard`（Player 2，静止靶）
- 第 1 次尝试：`aim_and_fire` 返回 `reason='verify_failed'`；`scan_adaptive` 的候选是 22 次反弹、180m 超程的
  `reachable=False` 路径（`hit=False`）——按设计被拒绝，未开火。
- 第 2 次尝试：找到 **10 次反弹、118.35m** 的路径，`raycast` 复核 `hit=True, hit_pid='<pid-2>', self_hit=False, self_risk_ok=True`
  → 开火；随后 `kills_of` 从 `{'kills':0,'victories':0}` 变为 **`{'kills':1,'victories':1}`**。
- 计分复核（`gc.getScores()`）：`<pid-1>` 的 `type=0`（击杀）`value=1`；本地局一击必杀后回合立即重置
  （`round_id=<round-id>`，双方重新存活）——与 `kit` 注释"本地局用比分增量判命中"一致。
- 截图（计分板 `Player 1 1:1 / Player 2 0:1`）：`ego-kill-confirmed.png`（本机工作区，未入库）。

复现脚本（要点）：

```python
kit = await Kit(port=45339).connect()
my = await kit.my_pid('arrows')                 # <pid-1>
target = (await kit.opponents(my))[0]           # <pid-2>
tp = await kit.position(target)
r = await kit.aim_and_fire(my, tp, target_id=target, fire_sec=0.9)   # 转向+复核+开火
# r = {'fired': True, 'angle_deg': -141.73, 'verify': {... 'hit_pid': '<pid-2>' ...}}
# 用分数增量判定命中：kills_of(my) 0 -> 1
```

**结论**：真实本地局上，"角色固定 → 选角（含反弹路径）→ 转向 → 实际朝向复核 → 开火 → 比分归因"整条火控链路可用，
一次击杀完成；`ttkit` 对不可达路径的拒绝与自伤检查也按预期生效。
